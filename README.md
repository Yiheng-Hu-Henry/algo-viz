# algo-viz

一个单文件、零依赖的算法可视化页面：排序的每一次比较、寻路的每一步扩展，都在画布上。

打开 `index.html` 就能用 —— 没有构建、没有 npm、没有 CDN。

## 排序

五种算法，可调规模（8~80）和速度：

| 算法 | 特点 |
| --- | --- |
| 冒泡排序 | 相邻交换，每轮把最大值冒到末尾 |
| 插入排序 | 维护有序前缀，逐个插入 |
| 选择排序 | 每轮选最小值放到前面 |
| 快速排序 | Lomuto 分区，递归处理两侧 |
| 归并排序 | 递归分半后合并回写 |

统计比较次数、交换次数、写入次数、总步数和实际耗时。同样规模下切换算法，
比较/交换的差异会非常直观 —— 比如快排的交换远少于冒泡，归并几乎只做写入。

## 寻路

46 × 21 的网格，四种算法：

| 算法 | 说明 |
| --- | --- |
| BFS | 等权最短路，一圈圈扩散 |
| DFS | 一条路走到黑，路径通常很长 |
| Dijkstra | 按代价扩展，会绕开高代价格 |
| A* | 代价 + 曼哈顿距离，扩展格数明显少于 Dijkstra |

每个格子有 1 / 2 / 4 三种地形代价（颜色深浅不同）。BFS 无视代价直接穿过去，
Dijkstra 和 A* 会绕路 —— 这是「有权图不能只用 BFS」最直观的演示。

### 交互

- 拖动绿色起点或红色终点改变位置
- 空白处拖拽画墙，墙上拖拽擦除
- 「生成迷宫」用递归回溯挖出完美迷宫（任意两点连通、无环）
- 「随机障碍」撒 28% 的墙

## 实现说明

**算法写成生成器。** 每个排序算法是 `function*`，每一步 `yield` 一个操作：

```js
{ type: 'compare', indices: [j, j + 1] }
{ type: 'swap',    indices: [j, j + 1] }
{ type: 'write',   indices: [i], value: 42 }
{ type: 'sorted',  indices: [i] }
```

这样算法本身保持教科书的写法（没有为了动画而加的 `await` 或回调），播放器只负责
把操作重放到显示数组上。生成器操作的是数组副本，播放器同步改显示数组，两边不会跑偏。

**高速时批量绘制。** 速度滑到最右时单步延迟为 0，此时每帧应用 18 步再调用一次
`requestAnimationFrame` —— 逐个 `fillRect` 会把主线程压垮，表现成「越快越卡」。
现在 80 根柱子的冒泡排序能在几百毫秒内播完。

**暂停不销毁状态。** 暂停用的是 `while (paused) await sleep(60)`，而不是中断生成器。
中断意味着要支持「从中间恢复」，而生成器的迭代状态一旦丢失就没法恢复 —— 用等待
换来实现上的简单，代价是暂停期间有个 60 毫秒的空转。

**Canvas 按 DPR 缩放。** `setupCanvas()` 每次重绘都重设 `canvas.width = 逻辑宽 × DPR`
并 `ctx.setTransform(ratio, ...)`，这样在 2 倍屏上线条和柱体边缘不会发虚。

## 测试

```bash
node test/verify.mjs
```

页面没有构建步骤，也就没有可以直接 `import` 的模块。测试的做法是：读取 `index.html`，
用 `node:vm` 加一层最小 DOM 桩执行页面脚本，再从作用域里取出算法函数验证：

- 5 种排序：随机数组 30 轮，检查结果有序、元素不丢不增
- 4 种寻路：随机起终点 20 轮，检查路径首尾正确、相邻格相连、不穿墙；BFS 额外验证路径长度等于曼哈顿距离 + 1
- 迷宫：通道占比、起点终点可通行、两点连通
- 绘制：调用 `drawSort` / `drawPath`，用记录型 ctx 桩确认确实发出了对应数量的 `fillRect`

## 限制

- 只做二维网格寻路，没有权重图、没有对角线移动
- 排序固定为升序，不支持自定义比较器
- 迷宫尺寸按画布比例写死（46 × 21）
